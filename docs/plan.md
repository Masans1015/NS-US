## 0. v1.0 で何が破綻していたか

検算して見つかった問題を、影響の大きい順に並べる。**すべて算術か定義の不整合であり、実装の巧拙とは無関係。**

| # | 問題 | v1.0 の記述 | 実際 |

## 2. 8本が入らないことの証明

工数を全部足す。**未計上だった3項目を加えるのが精緻化の本体。**

| 費目 | v1.0 | v1.1 | 根拠 |
|---|---|---|---|
| 基盤（W1-2） | 30h | **27h** | W1が12h・W2が15h |
| アプリ実装 8本 | 156h | 156h | requirements.md の工数列（変更なし） |
| 評価セット作成 | 計上なし | **+18h** | 150ケース×6分＋injection 20件×10分 |
| Before実測 | 計上なし | **+12h** | 8アプリ分（A15・A18は各2h、他は1〜1.5h） |
| telemetry回収・集計 | 計上なし | **+6h** | 13週×0.5h |
| **必要合計** | 186h | **219h** | |
| **稼働** | 195h（想定） | **174h**（実額） | |
| **差** | -9h | **-45h** | |

楽観ケース（祝日も稼働して195h確保）でも `219 - 195 = -24h`。
**どちらの前提でも8本は入らない。** これは削るか削らないかの判断ではなく、算術の結果。

「未計上分を諦めれば8本入る」は成立しない。諦める対象が評価セットだから、
P3ゲート（加重スコアが閾値超え）を通せず、telemetry も集計されず、
**外販根拠が一切出ないまま8本のプロトタイプが残る**。13週の目的そのものを失う。

### 削る対象の選定

`docs/requirements.md` は A14／A13 を削り候補として明示している。それでも足りない（-45h に対し、2本削っても実質 -34h）ので、もう1本要る。

| ID | 工数 | 13週内で得られるもの | 判定 |
|---|---|---|---|
| A15 | 30h | 型キットの抽出元。A11の見積ロジックの前提 | **確定**（他が依存する） |
| A03 | 10h | 外販性◎。日常利用でG1到達見込みが最も高い | **確定** |
| A04 | 12h | 外販性◎。A03とpolicyブロックを共有し実装が軽い | **確定** |
| A11 | 30h | 外販性○。Citations で網羅率を機械検証できる（§5参照） | **確定** |
| A09 | 20h | 外販性✕だが自分の利用頻度が最も高い。時間削減の実額が最大 | **確定** |
| A13 | 15h | 顧客案件の発生タイミング依存 | **条件付き**（W11時点でバッファ15h以上なら着手） |
| A18 | 24h | 合成データ評価のみ。契約受領頻度が低くG1に到達しない。HITL全件法務で短縮効果も限定 | **次期送り** |
| A14 | 15h | 競合多数、差別化は測定可能性の判定のみ | **次期送り** |

確定5本＝`30+10+12+30+20 = 102h`。未計上分（評価セット15h＋実測8h＋集計6h＝29h）を足して **131h**。
稼働174hに対し **バッファ43h（25%）**。A13 を条件付きで拾っても149h、バッファ25h（14%）。ここで初めて計画が成立する。

未計上分が8本時の36hから29hに減るのは、評価セットが150→120ケース、実測が8→5アプリになるため。

**A18 を落とすのは「重要でない」からではない。** 13週内に G1（自分の継続利用）へ到達できる構造がないため、
今期やっても「合成データで評価スコアが出た」以上のものが残らない。実データを扱える条件が整った期に回すほうが実入りが大きい。

## 4. ゲート体系の整合

### G番号の確定

`CLAUDE.md` の DoD と `rubric.portability_check` が「G5」を参照しているのに、
`docs/requirements.md` のゲート表は G1〜G3 しかなかった。番号を確定させる。

| ゲート | 内容 | 通過条件 | 落ちたときの扱い |
|---|---|---|---|
| G1 | 自分 | §後述の改定基準 | 廃棄（習熟としては計上する） |
| G2 | チーム | 自分以外2名が各3回以上使用、実測ログ10件以上 | 社内専用として据え置き |
| G3 | 顧客 | 顧客1社でパイロット完了 | 外販は見送り、社内資産として運用 |
| G4 | ガバナンス | セキュリティ／ガバナンス審査パス（P5と同一） | 外販不可。社内利用は継続 |
| G5 | 可搬性 | org-profile 差し替え後のスコア低下が `rubric.portability_check.max_score_drop` 以内、かつ代替モデルで動作 | core に会社固有が漏れている。分離をやり直す |

**判定順序は番号順ではない。** `G5 → G1 → G2 → G4 → G3`。
G5 は最も早く（P3の採点と同時に）判定できて最も安く直せるので先に置く。
番号は識別子であり、順序を表さない。

A09 は G5 免除・G3 対象外（社内専用と定義済み）。ただし core／org の分離構造は他と同じに保つ。

### G1 の改定（最重要）

**旧基準:「直近2週の利用が5日以上」は日次利用アプリしか通れない。**
RFPは週5回来ない。契約書も、見積も、KPIツリーも来ない。
旧基準のままだと A11／A15／A13 は品質と無関係に自動的に廃棄される。**ゲートが測っているのは業務の発生頻度であって、アプリの価値ではない。**

新基準に差し替える。

> **G1（改定）**: 直近4週において、対象タスクが発生した機会のうち **80%以上** でアプリを使ったこと。
> ただし機会が **3回以上** 発生している場合に限り判定する。
> 機会が3回未満の場合は「判定保留」とし、次期へ繰越す。**廃棄しない。**

- 機会の回数は telemetry のレコード数と `free_note`（使わなかった理由）で数える。**使わなかった機会を記録しないと分母が消える**ので、使わなかったときも1レコード出す
- 日次利用アプリ（A03／A04）は「機会＝判断に迷った回数」なので、実質的に旧基準と同等の厳しさになる
- 「機会が3回未満なら保留」は逃げ道ではない。**発生頻度が低い業務にアプリを作った判断自体を次期に見直す**という意味

## 5. LLM 呼び出しの標準形

v1.0 は「外部LLM呼び出しは Anthropic API のみ。モデルは差し替え可能な形で定数化」までしか決めていなかった。
実装が始まってから毎回考え直すことになるので、ここで固定する。詳細と根拠は `docs/decisions.md` の ADR-005／ADR-006。

### 二層に分ける

| 層 | 対象 | LLM | 理由 |
|---|---|---|---|
| 決定論層 | **A03・A04** | 使わない | 全社員に配るアプリで各人にAPIキーを持たせるのは非現実的。区分判定は `policy.data_classification` と `prohibited_inputs[].detect_patterns` で機械判定できる。Go基準「見逃し0件」は決定論のほうが達成しやすい |
| LLM層 | A15・A11・A09・（A13） | 使う | 利用者は自分のみ。APIキーはセッション中のみJS変数で保持（`localStorage` 禁止は既定通り） |

A03／A04 で LLM を使うのは「匿名化案の文面生成」だけに限り、**キー未入力でも本体機能が完全に動く**構成にする。
これは制約への妥協ではなく、外販性◎の2本を「導入時にAPIキー調達が不要な製品」にするという設計判断。

### 呼び出し規約

```js
const MODEL = { PRIMARY: 'claude-opus-5', ALT: 'claude-sonnet-5' };
```

- モデルIDに日付サフィックスを付けない。`ALT` は G5 可搬性テストの代替モデル
- `thinking: { type: 'adaptive' }`。**`budget_tokens` は Opus 5／Sonnet 5 では 400 エラー**になる
- 深さは `output_config.effort`（既定 `high`、単純な抽出は `low`）で制御する
- 出力は `output_config: { format: {...} }` の構造化出力。**assistant prefill は 400 エラー**なので使えない
  → core は構造化データを返し、体裁は render 層が解釈する。3層分離とそのまま一致する
- `stop_reason === 'refusal'` を必ず確認する。**A04（規程違反の判定）と A18（レッドフラグ検出）は安全性分類器に拒否される経路がある。** サーバサイドフォールバックを既定で入れる
- 長文（RFP・契約書）は streaming。非streaming の `max_tokens` は 16000 目安
- プロンプトキャッシュ: core の system prompt ＋ org-profile を prefix に置き `cache_control`。1024トークン未満はキャッシュされない
- トークン数は `count_tokens` エンドポイントで測る。他社トークナイザで代用しない

### A11 の網羅率を機械検証する

A11 の Go基準は「必須要件の抽出漏れ0件」だが、v1.0 には検証手段がなかった。

RFP の PDF を base64 の `document` ブロックで直接投入し、`citations: { enabled: true }` を付ける。
出力の各要件に出典（ページ番号）が付くので、**抽出漏れを人が原文と突き合わせて確認できる**。
上限は32MB／600ページ（1Mコンテキストモデル）。これを超えるRFPは分割する。

C2（網羅性）の `check_method` を `deterministic` にできるかはこの出典が付くかどうかで決まる。
**W8 の最初の作業は Citations の動作確認**にする。動かなければ C2 は `human` 判定に落とす（`docs/requirements.md` §3 の一貫性テストの手順と同じ扱い）。

## 6. 未計上だった費目

### 評価セット（15h）

確定5本で 20+30+30+20+20 = **120ケース**（A18を落としたので150→120）、injection_suite 20件。
`120件×6分＋20件×10分 ≒ 15h`。

2段構えにして前倒し工数を圧縮する。

| 時点 | 件数 | 根拠 |
|---|---|---|
| P3 Go/No-Go | 全アプリ **20件** | `evalset.schema.json` の `minItems` を満たす最小 |
| P4 パイロットまで | A03/A04 は **30件** | requirements.md §3 の規定件数 |

A03 の禁止入力ケースは `policy.prohibited_inputs[].detect_patterns` から**機械生成できる**（正規表現に対する陽性・陰性例）。
手で書くのは境界ケースと敵対的ケースだけにする。これで A03/A04 の30件が現実的になる。

`sanitization.method` は A03/A04/A18 は「合成データ」、A15/A11/A09 は「手動マスキング」を既定とする。

### Before 実測（8h）

**P1ゲートは「現状値が実測で埋まっていること」。推定値で埋めた時点で13週の成果が主張できなくなる。**
手順は `docs/baseline-measurement.md` に分離した。W1 の初日（09/01）から並行して開始する。

### API 利用費（計画費目として計上）

Opus 5 は input $5／output $25 per MTok。

| 用途 | 概算 |
|---|---|
| 開発中の評価実行（120件×3回の改善反復） | 約 $90 |
| 一貫性テスト（llm_judge 項目 × 5件 × 3回） | 約 $15 |
| 13週の実運用利用（約150回） | 約 $40 |
| **合計** | **約 $145〜250（2.2万〜3.8万円）** |

プロンプトキャッシュを効かせれば input 側は大幅に下がる。
**月1万円を上限に置き、超えたら `effort` を下げるか `MODEL.ALT`（Sonnet 5、$3/$15）に落とす。** 本数を削るより先にここを削る。

### telemetry 回収・集計（6h）

W1 の基盤に集計スクリプトを含める（ADR-010）。DoD が要求するのは「出力できること」だが、
出力しただけでは `削減時間 = baseline − (actual + manual_fix)` が出ない。**集計手段がないと外販根拠は存在しない。**

出す数字は `docs/externalization-kit.md` の「集計の型」に揃える。n<10 は提示しない。

## 8. 週次の運用リズム

毎週金曜（祝日なら前営業日）に30分。**これも稼働174hの内側**（§6の集計6hに含む）。

1. telemetry をダウンロードして `telemetry/{app_id}.{YYYY-MM}.jsonl` に追記し、集計スクリプトを回す
2. `./scripts/check-separation.sh` を実行
3. 残工数と残バッファを §3 の表と突き合わせる。**超過が2週続いたら本数を削る**（機能を削るのではなく本数を削る）
4. 実運用で失敗したケースを evalset に `origin: "failure_promoted"` で追加する
5. §7 の期限が到来していないか確認する
