覆すときは新しい ADR を追加し、旧 ADR には「棄却（ADR-0NN による）」と書く。上書き削除はしない。

## ADR-001 稼働時間の前提を174hに固定する

**判断**: 計画の基礎を「平日3h／日・祝日は稼働0」＝13週で **174h** とする。「週15h」は努力値として扱い、計画の基礎に使わない。

**理由**: 2026年9〜11月に祝日が6日ある（9/21・9/22・9/23・10/12・11/3・11/23）。
13週×15h＝195h の前提は21h過大。とくに W4（9/21-27）は平日2日で稼働6hしかなく、この週に集中作業を置くと確実に遅れる。

**影響**: `docs/plan.md` §1 の週別稼働時間表が唯一の基礎になる。祝日に稼働できた分はバッファの回復として扱い、計画の前提には織り込まない。

## ADR-002 ポートフォリオを確定5本＋条件付き1本に縮小する

**判断**: **A15・A03・A04・A11・A09 を確定**。A13 を条件付き（W11時点で残バッファ15h以上なら着手）。**A18・A14 を次期送り**。

**理由**: 必要工数219h（基盤27h＋実装156h＋未計上36h）に対し稼働174h。**超過45h。**
楽観ケース（195h）でも24h超過するので、**稼働時間の前提を変えても結論が変わらない**。
確定5本なら131h（実装102h＋未計上29h）で、稼働174hに対しバッファ43h（25%）。

「未計上分を諦めて8本やる」は成立しない。諦める対象が評価セット作成なので、P3ゲートを通せず telemetry も集計されず、外販根拠がゼロのまま8本のプロトタイプが残る。13週の目的を失う。

A18 を落とした理由は重要度ではなく **13週内に G1 へ到達する構造がないこと**。契約書の受領頻度が低く、実データ投入も最終段まで行わない方針なので、今期の成果は「合成データで評価スコアが出た」に留まる。実データを扱える条件が整った期に回すほうが実入りが大きい。

**影響**: `docs/requirements.md` §1 の8本の要件定義は残す（次期に使う）。着手対象のみ `docs/plan.md` §2 が上書きする。

**代替案と棄却理由**: A14/A13 の2本だけ落とす（-30h＋未計上分の減少で実質-34h）→ 必要185h、まだ11h超過。
バッファなしで13週走ることになり、1回の遅れで復帰不能。

## ADR-003 ゲート番号を G1〜G5 に確定し、判定順序を明示する

**判断**: G1 自分／G2 チーム／G3 顧客／**G4 ガバナンス審査（新設）**／**G5 可搬性（定義）**。
判定順序は番号順ではなく `G5 → G1 → G2 → G4 → G3`。

**理由**: `CLAUDE.md` の DoD と `rubric.portability_check` が「G5」を参照しているのに、
`docs/requirements.md` のゲート表には G1〜G3 しかなく、G4/G5 が未定義だった。参照先のない条件は運用されない。

G5 を先頭に置くのは、P3の採点と同時に判定でき、落ちたときの修正（core からの分離やり直し）が最も安いから。
後段で見つけると作り直しの量が増える。

**影響**: `docs/requirements.md` §4 のゲート表を差し替え済み。番号は識別子であり順序を表さないことを明記した。

## ADR-004 G1 を「利用日数」から「機会利用率」に改める

**判断**: G1 を次に差し替える。

> 直近4週で、対象タスクが発生した機会のうち80%以上でアプリを使った。ただし機会が3回以上発生した場合に限り判定する。3回未満は「判定保留」として次期へ繰越し、**廃棄しない**。

**理由**: 旧基準「直近2週の利用が5日以上」は日次利用アプリしか通れない。
RFP・契約書・工数見積・KPIツリーは週5回発生しない。旧基準のままだと A11／A15／A13 が品質と無関係に自動廃棄される。
**旧基準が測っていたのは業務の発生頻度であって、アプリの価値ではない。**

**影響**: 使わなかった機会も telemetry に1レコード出す運用が必要になる（`free_note` に理由を書く）。
記録しないと分母が消えて利用率が計算できない。日次利用の A03／A04 は「機会＝判断に迷った回数」なので実質的な厳しさは変わらない。

「機会3回未満なら保留」は逃げ道ではない。**発生頻度の低い業務にアプリを作った判断自体を次期に見直す**という意味。

## ADR-005 A03・A04 を LLM 非依存で成立させる

**判断**: A03（データ投入可否ゲート）と A04（AI利用ポリシー・チェッカー）の**本体機能に LLM を使わない**。
決定論的判定（`policy.data_classification` の区分判定木＋`prohibited_inputs[].detect_patterns` の正規表現）だけで成立させる。
LLM は「匿名化案の文面生成」だけに任意で使い、**APIキー未入力でも本体機能が完全に動く**構成にする。

**理由**: この2本は利用者が全社員。TierA（単体HTML・ブラウザ内完結）で全社員に配るなら、
各人が Anthropic API キーを持つか、キーをファイルに埋めて配布するかしかない。前者は非現実的、後者は事故。

かつ A03 の Go基準は「禁止入力の見逃し0件」。**足切り条件を LLM の確率的判定に乗せるべきではない。**
正規表現とルールツリーのほうが達成しやすく、検証もしやすい。

**影響**: 外販性◎の2本が「導入時にAPIキー調達が不要な製品」になる。制約への妥協ではなく、この2本を最も売りやすい形にする判断。
A03/A04 の rubric は `check_method: deterministic` を全面的に使えるので、一貫性テスト（llm_judge向け）も不要になる。

## ADR-006 LLM 呼び出しの規約を固定する

**判断**: LLM層（A15・A11・A09・A13）の呼び出し規約を以下に固定する。

```js
const MODEL = { PRIMARY: 'claude-opus-5', ALT: 'claude-sonnet-5' };
```

| 項目 | 規約 |
|---|---|
| モデルID | 日付サフィックスを付けない。`ALT` は G5 可搬性テストの代替モデル |
| 思考 | `thinking: { type: 'adaptive' }`。**`budget_tokens` は Opus 5／Sonnet 5 で 400 エラー** |
| 深さ | `output_config.effort`（既定 `high`、単純抽出は `low`）で制御 |
| 出力 | `output_config: { format: {...} }` の構造化出力。**assistant prefill は 400 エラー**なので使えない |
| 拒否 | `stop_reason === 'refusal'` を必ず確認し、サーバサイドフォールバックを入れる |
| 長文 | streaming。非streaming の `max_tokens` は 16000 目安 |
| キャッシュ | core の system prompt ＋ org-profile を prefix に置き `cache_control`。1024トークン未満はキャッシュされない |
| トークン計測 | `count_tokens` エンドポイント。他社トークナイザで代用しない |

**理由**: v1.0 は「モデルは差し替え可能な形で定数化する」までしか決めておらず、
毎アプリで考え直すことになっていた。とくに次の2点は事故になる。

- **prefill が使えない**: 章立てや出力形式を強制する定番手法が 400 エラーになる。
  構造化出力に切り替えると、core が構造化データを返し render が体裁を解釈する形になり、**3層分離とそのまま一致する**。制約が設計を正しい方向に押している
- **refusal を握りつぶす経路**: A04 は「規程違反の判定」、A18 は「レッドフラグ検出」を扱う。
  安全性分類器に拒否されて `stop_reason: "refusal"`（HTTP 200）が返る経路がある。
  `content` を先に読む実装だと**空の結果を「違反なし」と誤表示する**。A04 の性質上これは最悪の失敗

**影響**: `core/` に置くのは呼び出し規約ではなくプロンプトと判断ロジックのみ。上記の規約は共通シェル（W2）に1箇所で実装する。

## ADR-007 評価セットを P3／P4 の2段にする

**判断**: P3 Go/No-Go は全アプリ **20件**（`evalset.schema.json` の `minItems`）。
`docs/requirements.md` §3 が30件を要求する A03／A04 は、**P4 パイロットまでに30件へ拡張**する。

加えて、A03 の禁止入力ケースは `policy.prohibited_inputs[].detect_patterns` から**機械生成する**（各正規表現に対する陽性例・陰性例）。手で書くのは境界ケースと敵対的ケースだけ。

**理由**: 確定5本で120ケース＋injection 20件。手書きだと約15h で、確定5本の実装102hの15%に達する。
一方 P3 は「閾値超え＋足切り全通過」の判定であり、20件で通らないものが30件で通ることはない。
**件数が要るのは精度の主張（P4以降）であって、Go/No-Go の判定ではない。**

**影響**: A03 の足切り「禁止入力の見逃し0件」は機械生成ケースで網羅的に検証できるようになり、
手書きより**むしろ強くなる**。`sanitization.method` は A03/A04 が「合成データ」、A15/A11/A09 が「手動マスキング」。

## ADR-008 API 利用費を計画費目として計上する

**判断**: 13週の API 利用費を **約$145〜250（2.2万〜3.8万円）** と見積り、**月1万円を上限**とする。
超えたら `effort` を下げるか `MODEL.ALT`（Sonnet 5、$3/$15）に落とす。**本数を削るより先にここを削る。**

**理由**: v1.0 は工数だけを管理していて費用の記載がなかった。
評価セット120件を改善反復3回で回すと約360回の採点呼び出しが発生する。ここが費用の主要因で、
実運用の利用（約150回）よりも大きい。上限を先に決めておかないと、費用を理由に評価の回数を削ることになる。**評価を削ると外販根拠が消える。**

**影響**: プロンプトキャッシュ（ADR-006）が費用対策の主手段になる。core の system prompt と org-profile は毎回同じなので prefix に置けば効く。

## ADR-009 IP帰属の方針決定を W13 から W2 に前倒しする

**判断**: RCG業務中の成果を NouScale 資産として扱う方針の決定を、**W2末（09/13）** に前倒しする。文書化は W13 のまま。

**理由**: `docs/requirements.md` §5 の見送りリスト #7 が「W13の次期計画までに方針を決める。遅れるほど整理が難しくなる」と自ら書いている。
**13週分の成果が積み上がってから帰属を整理するのが最も難しい。** 実装0hで済む判断を最後に置く理由がない。

**影響**: W2末までに方針が出ない場合、W3以降のコミットに帰属の記録を残す運用で暫定対応する（後から遡って整理できる状態を保つ）。

## ADR-010 telemetry 集計スクリプトを W1 の基盤スコープに含める

**判断**: W1 の基盤①に、記録・エクスポートに加えて**集計スクリプト**を含める。

**理由**: DoD は「telemetry を1回の利用につき1レコード出力できる」までしか要求していない。
しかし出力しただけでは `削減時間 = baseline − (actual + manual_fix)` は出ない。
**集計手段がなければ外販根拠は存在しない。** 出力と集計は同時に作るのが最も安い（スキーマが手元にある状態で作れる）。

**影響**: 出す数字は `docs/externalization-kit.md` の「集計の型」に揃える。中央値とレンジ（p25-p75）、件数併記、n<10 は提示しない。
`docs/plan.md` §8 の週次リズムで毎週回す。
