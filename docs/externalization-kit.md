# 外部化スキーマキット v1.0

社内利用を先行し、そのまま外販へ運べる構造を最初から確保するための最小セット。
実装に着手する前に、このファイルと `AIアプリ8本_要件定義P1_v1.0.xlsx` の「外部化スキーマ」シートを読むこと。

---

## この設計が解いている問題

社内向けに作ったアプリは、必ず自社の文脈にハードコードされる。提案フォーマット、標準条項、工数実績、規程の条文。
動くものができた時点では気づかず、外販しようとした瞬間に「剥がせない」ことが判明する。結果、一から作り直しになる。

「あとで外販できるようにする」は成立しない。**最初から剥がせる構造で作って、社内で使う**しかない。

その分離を、規律ではなくファイル構造で担保するのがこのキットの目的。

## 3層の責務

| 層 | 置くもの | 置いてはいけないもの |
|---|---|---|
| **core** | 分解の型、検査ロジック、欠落検出、判定アルゴリズム、汎用の検品項目 | 会社名、自社の規程条文、自社の工数実績、自社の章立て、色とフォント |
| **org** | データ区分、禁止入力、承認済みツール、工数実績、標準条項、章立て、トーン | 判断のアルゴリズム |
| **render** | フォント、色、レイアウト、生成に使うスキル名 | 内容に関わる判断 |

**何を書くかは core、どう見せるかは render、誰の話かは org。**

## 分離できているかの検査

人の注意力で担保しない。各アプリの完成判定に、次の検索を入れる。

```bash
grep -riE "ライズ|RCG|NouScale|游ゴシック|株式会社" core/
```

1件でもヒットしたら分離に失敗している。機能を足すのではなく、分離をやり直す。

## 可搬性テスト（G5）

外販判断の前提。以下で合格を判定する。

1. `org/org-profile.rcg.json` を、架空の別企業プロファイルに差し替える
2. 同じ評価セットで採点する
3. スコアの低下が `rubric.portability_check.max_score_drop` 以内なら合格

低下が大きい場合、core に会社固有が漏れている。どの評価ケースで落ちたかを見れば、漏れている箇所が特定できる。

代替LLMでの動作確認も同時に行う。特定モデルの癖に依存した core は、モデル更新で壊れる。

## 4ファイルの役割

### org-profile.schema.json
会社固有設定の唯一の置き場。**外販時に差し替えるのはこのファイルだけ**という状態を維持する。

`delivery` `document` `legal` の3ブロックは空でも動く設計にしてある。
顧客は最初 `policy` だけを埋めれば使い始められ、使いながら残りが育つ。
空を許さない設計にすると導入前に大量のヒアリングが必要になり、売れなくなる。

### rubric.schema.json
評価基準。判定方法は `deterministic`（機械判定）を最優先し、`llm_judge` は一貫性テストとセットで使う。
`must_pass_criteria` に安全性の軸を必ず入れること。加重平均が高くても、安全性が落ちたら全体不合格。

### telemetry.schema.json
**後から遡って取得できない唯一のデータ。** 外販時の効果根拠はこれしかない。

特に後付けが効かない2項目:

- `actual.manual_fix_minutes` — 出力後の手直し時間。計上しないと削減率が2倍近く過大に出る
- `consent.external_citation_anonymized` — 半年後に「あの案件を事例に使いたい」となったとき、記録がなければ使えない

初回から入れておけば追加コストはほぼゼロ。後から追加するコストは、それまでのデータが全部使えなくなること。

### evalset.schema.json
テストケース集。`origin: "failure_promoted"` の比率が上がるほど実戦的になる。
実運用で失敗したケースをここへ昇格させる運用が、アプリを使うほど強くする唯一の仕組み。

外部文書を扱うアプリ（A11 RFPアナライザー、A18 契約スクリーニング）は `injection_suite` が必須。

## 集計の型

外販時に出す数字は、この形に揃える。

| 指標 | 計算 | 提示 |
|---|---|---|
| 削減時間 | `baseline − (actual + manual_fix)` | 中央値とレンジ（p25-p75） |
| 削減率 | 削減時間 ÷ baseline | 件数を必ず併記。n<10 は提示しない |
| 品質維持 | `accepted_without_rework` の割合 | 削減率と必ずセットで |
| 継続利用 | 直近4週の利用日数 ÷ 営業日 | 習熟の証跡 |

時間だけ示すと「雑になっただけ」と疑われる。品質指標を必ず並べる。

## 実装時の注意

- **TierAはブラウザ内完結。** 情シス承認が未確認のため、Supabase / Vercel は当面使わない。telemetry は都度ダウンロードで回収する
- **org-profile はアプリに埋め込まず、ファイル読込にする。** 埋め込んだ瞬間に差し替えができなくなる
- **A18 は合成データのみ。** 実データの投入は最終段まで行わない
- **A09 は G5 免除。** ただし免除するのはテストの実施だけで、core/org の分離は他と同じ構造を維持する

---

## バージョン

すべてのスキーマに `schema_version` を持たせてある。
core と org-profile のバージョンが食い違ったまま動くと、原因の分からない品質低下として現れる。
起動時に検証し、不一致なら止めること。
