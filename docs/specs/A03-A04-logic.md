# A03・A04 判定ロジック詳細設計（LLM非依存）

対象週: A03 = W6（10h）／A04 = W7（12h）
前提: ADR-005（LLM非依存）、`docs/requirements.md` の A03・A04 節

この2本は**利用者が全社員**で、外販性◎の主力。`policy` ブロックを共有するが、
**判定の倒し方は逆**（§4）。共有するのはデータだけで、閾値設計は別物。

---

## 1. 設計の中心となる制約

### 自由文からデータ区分を当てることは原理的にできない

A03 の入力は「投入予定のテキスト」。ここから区分を推定しようとすると壁に当たる。

- **匿名化済みの顧客資料は、見た目が社内文書と区別できない。** 顧客名を伏せた議事録は、
  文面上は社内会議のメモと同じ。level 2 と level 3 を機械で分けられない
- 逆に「社内規程」と「顧客の社内規程」も文面が似る
- 判定を外すと、A03 の足切り「**禁止入力の見逃し0件**」を守れない

したがって、**区分は利用者に選ばせる**（ADR-013）。機械が担うのは次の2つに絞る。

| 機械が担う | 人が担う |
|---|---|
| 禁止入力の検出（`detect_patterns` の正規表現） | データ区分の選択 |
| 選ばれた区分に対する可否・条件・使用可能ツールの導出 | 迷ったときにどちらを選ぶか |
| 匿名化すべき箇所の指摘 | 匿名化の実施と確認 |

これは機能の後退ではない。**判定所要時間30秒以内**というKPIに対し、
区分の選択は数秒で終わり、規程の条文を引く部分（時間がかかる部分）を機械が肩代わりする。

### Go基準の読み替えが必要

要件定義は「評価30件で、**区分判定の正答率95%以上**・禁止入力の見逃し0件」と書いている。
区分を利用者が選ぶ設計では、前半は次の意味になる。

> 選択された区分に対する **可否・条件・使用可能ツールの導出**の正答率が95%以上

導出は `policy` の参照だけなので、実装が正しければ100%になる。
**したがって A03 の実質的な合否は「禁止入力の見逃し0件」に集約される。**
評価30件の設計もそこへ寄せる（§5）。

> **要確認**: この読み替えは要件定義の解釈変更にあたる。W6 着手前（10/04まで）に確定させる。
> 確定しない場合は「区分の自動推定を補助表示として出し、正答率はその補助表示に対して測る」で進める。

## 2. A03 判定木

上から順に評価し、**最初に確定した時点で打ち切る**。

```
入力テキスト ＋ 利用者が選んだ区分
│
├─ 1. prohibited_inputs[] の detect_patterns を全件走査
│     ヒット → 【不可】
│              該当 label / rationale / source_document を表示
│              マッチ箇所をハイライト
│     ※区分によらず禁止。区分判定より必ず先に評価する
│
├─ 2. 選択区分の ai_input を見る
│     "prohibited"  → 【不可】 definition と examples を表示
│     "allowed"     → 【可】   allowed_tools を表示
│     "conditional" → 3へ
│
├─ 3. conditions[] を表示し、【条件付き可】
│     allowed_tools（∩ approved_tools[].status === "approved"）を表示
│     detect_patterns のうち「禁止ではないが要匿名化」のものを走査し、
│     マスク候補として提示
│
└─ 4. 匿名化案の文面生成（任意・LLM）
      LLM.available() === false でも 1〜3 は完全に動く
```

### 実装上の要件

- **正規表現は `detect_patterns` から読む。コードに書かない。** 書いた瞬間に外販時の差し替えが効かなくなる
- 正規表現の実行はブラウザ内。入力テキストを外部送信しない（要件定義の「処理はブラウザ内で完結」）
- `detect_patterns` が不正な正規表現なら**起動時に停止**する。実行時に黙って false を返すと見逃しになる
- マッチ箇所のハイライトは、`RegExp` の `d` フラグ（`hasIndices`）で位置を取る
- 走査は**全パターンを実行する**。1件ヒットで打ち切らない。「他にも触れている」を全部見せる

### 出力

```json
{
  "verdict": "prohibited | conditional | allowed",
  "matched_prohibitions": [
    { "label": "...", "rationale": "...", "source_document": "...",
      "matches": [{ "text": "...", "start": 0, "end": 0 }] } ],
  "classification": { "level": 3, "label": "社内限", "ai_input": "conditional" },
  "conditions": ["..."],
  "usable_tools": [{ "name": "...", "max_data_level": 3, "restrictions": ["..."] }],
  "anonymization_targets": [{ "text": "...", "reason": "...", "suggestion": "..." }]
}
```

`source_document` を必ず出す。**「なぜ不可なのか」を規程の条番号で示せないと、利用者は判定を信用せず回避する。**

## 3. A04 判定ロジック

A04 の入力は「実施計画文またはプロンプト」。ここも**自由文の全文マッチに頼らない**。
構造化された質問に答えさせ、`policy` と照合する。

### 入力（構造化）

| 項目 | 参照する org フィールド |
|---|---|
| 何をするか（自由文） | 補助検出のみ |
| 使うツール | `approved_tools[]` |
| 投入するデータの最も機微な区分 | `data_classification[]` |
| 成果物を社外に出すか | `disclosure_rules` |
| 該当する操作（複数選択） | `human_approval_required[]` |

### 照合規則

| # | 検査 | 抵触時の出力 |
|---|---|---|
| 1 | ツールが `approved_tools[]` にあるか | 未登録 → 【要確認】法務・情シスへ |
| 2 | `status !== "approved"` | 【不可】審査中のツールは使えない |
| 3 | 投入区分 > `max_data_level` | 【不可】該当条項＋代替ツールを提示 |
| 4 | `training_optout === false` かつ 区分 level ≤ 2 | 【不可】学習利用オフが担保されていない |
| 5 | 選択操作が `human_approval_required[]` に該当 | 【条件付き】必要な承認を明示 |
| 6 | 社外提出 かつ `disclosure_rules.external_required` | 【条件付き】`statement_template` を提示 |
| 7 | 自由文に `prohibited_inputs` の検出 | 【不可】該当ラベルを表示 |

1〜6 は**構造化入力に対する照合なので過検出が原理的に発生しない**。
過検出が出るのは 7 だけ。ここを絞ることで「過検出20%以下」を守る（§4）。

### 出力

```json
{
  "verdict": "prohibited | conditional | allowed | needs_review",
  "violations": [{ "check": 1, "reason": "...", "clause": "...", "alternative": "..." }],
  "required_approvals": ["..."],
  "disclosure_statement": "...",
  "next_action": "法務確認へ | 承認申請へ | そのまま実施可"
}
```

「抵触あり」で終わらせず **`alternative` と `next_action` を必ず出す。**
要件定義の既知リスクが「過検出が多いと使われなくなる」なので、
止めるだけの出力は使われなくなる方向に働く。

## 4. 2本で閾値の倒し方が逆になる

同じ `policy` を読むのに、最適化の方向が反対。**ここを混同すると両方壊れる。**

| | A03 | A04 |
|---|---|---|
| Go基準 | 禁止入力の**見逃し0件**（足切り） | 検出率100%・**過検出20%以下** |
| 優先する誤り | 過検出は許容 | 見逃しも過検出も許さない |
| 迷ったときの倒し方 | **厳しい側**（より機微な区分・不可寄り） | **構造化入力で曖昧さを消す**（倒さない） |
| 事故の形 | 誤って「可」と出す → 情報漏洩 | 過検出が多い → 使われなくなり規程が空文化 |

したがって:

- **A03 の `detect_patterns` は再現率優先**で書く。過検出は `conditional`（条件付き可）が吸収する
- **A04 は自由文マッチ（検査7）を最小限にする。** 検査1〜6の構造化照合を主経路にする
- **同じ正規表現セットを両アプリで同じ厳しさに使わない。** A04 は検出したものを
  「注意」として出し、`verdict` を直ちに `prohibited` にしない（検査7のみ）

## 5. 評価セット

P3 は20件、P4 までに30件（ADR-007）。`sanitization.method` は「合成データ」。

### A03（P3: 20件 → P4: 30件）

| tags | P3 | 狙い |
|---|---|---|
| 禁止入力・陽性 | 8 | `detect_patterns` の各パターンにつき1件以上。**足切りの本体** |
| 禁止入力・陰性 | 4 | 似ているが該当しない（例: 電話番号に見える製品番号）。過検出の確認 |
| 区分ごとの導出 | 4 | level 1-4 それぞれで可否・条件・ツールが正しく出るか |
| 境界 | 2 | 空入力、超長文、絵文字・全角半角混在 |
| 敵対的 | 2 | 「これは公開情報だから大丈夫」等、入力文中の自己申告 |

**陽性8件・陰性4件は `policy.prohibited_inputs[].detect_patterns` から機械生成する**（ADR-007）。
各正規表現に対し、マッチする最小文字列とマッチしない近傍文字列を自動で作る。
手で書くのは境界2件と敵対的2件だけ。**パターンを追加したら生成し直すので、
regex を足したのに評価が追いつかない状態が起きない。**

P4 への10件追加は、実運用で「判定に納得できなかった」ケースの `failure_promoted`。

### A04（P3: 20件 → P4: 30件）

| tags | P3 | 狙い |
|---|---|---|
| 既知の違反ケース | 8 | 検査1〜6 の各経路につき1件以上。**検出率100%が条件** |
| 適法ケース | 6 | 通るべきものが通るか。**過検出20%以下の分母** |
| 複合 | 3 | 複数の検査に同時に触れる（ツール未承認＋区分超過） |
| HITL要否 | 2 | `human_approval_required[]` の該当・非該当 |
| 敵対的 | 1 | 規程の抜け穴を突く書き方 |

適法ケース6件は**過検出率の測定に必須**。違反ケースだけの評価セットでは
「全部ダメと言う実装」が満点を取ってしまう。

## 6. 作業分解

### A03 = W6（10h）

| 作業 | 時間 |
|---|---|
| `core/A03.system.md`（判定木の仕様。プロンプトではなくロジック記述） | 2h |
| 判定木の実装（`apps/A03/index.html`） | 3h |
| `core/A03.rubric.json` | 1h |
| evalset 生成スクリプト＋手書き4件 | 2h |
| 採点・改善反復・G5（別社 policy へ差替え、低下0.3以内） | 2h |
| **計** | **10h** |

### A04 = W7（12h）

| 作業 | 時間 |
|---|---|
| `core/A04.system.md`（検査1〜7の仕様） | 2h |
| 構造化入力UI＋照合の実装 | 4h |
| `core/A04.rubric.json` | 1h |
| evalset 20件（違反8・適法6・複合3・HITL2・敵対1） | 3h |
| 採点・改善反復・G5 | 2h |
| **計** | **12h** |

A03 を先に作るのは、`policy` の読み方（区分・禁止入力・ツール）を A03 で確立してから
A04 が `human_approval_required` と `disclosure_rules` を足す形になり、**手戻りが出ないため。**

## 7. 配布（G2の前提）

この2本だけが「自分以外2名が各3回以上使用」（G2）を13週内に達成しうる。
配布は `dist/A03.html` の単体HTML（ADR-011）をファイル共有で渡す。

**ただし配布可否は情シス確認待ち（期限 W6末 10/11、`docs/plan.md` §7-1）。**
確定しない場合は G1 までで判定を止め、G2 は次期送り。

telemetry は各人がダウンロードしたファイルを回収する必要がある。
**回収経路が用意できないと G2 の「実測ログ10件以上」が満たせない。** 配布とセットで決める。
