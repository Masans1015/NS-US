## 1. core / org の切り分け（フィールド単位）

| 判断 | 置く層 | 参照先 |
|---|---|---|
| 案件概要から作業を分解する型 | **core** | — |
| 分解の粒度の決め方（どこで止めるか） | **core** | — |
| 不確実性の評価（何が読めていないか） | **core** | — |
| バッファの算定方法（式） | **core** | — |
| p50/p80 のレンジ提示ロジック | **core** | — |
| 前提の洗い出しと「外れたときの影響」の付与 | **core** | — |
| 情報不足箇所の指摘 | **core** | — |
| 作業種別ごとの実績工数 | org | `delivery.estimation_baseline[]` |
| ロール別の日次キャパシティ | org | `delivery.role_capacity[]` |
| バッファ率の具体値 | org | `delivery.buffer_policy` |
| フェーズ構成と比率 | org | `delivery.wbs_templates[]` |
| 出力の体裁 | render | `document.format_profile` |

**`core/A15.system.md` に書いてはいけないもの**: 具体的な時間数、フェーズ名の固定リスト、
会社名、ロール名の固定リスト。すべて org から差し込む。

### org が空のときの挙動（G5の前提）

`delivery` が空でも動くこと。これが外販時の初期状態。

| org の状態 | core の振る舞い |
|---|---|
| `estimation_baseline[]` が空 | 汎用レンジで出し、**各タスクの `basis` を `"judgment"` にする**。「実績なし」を出力に明示 |
| `wbs_templates[]` が空 | core の汎用フェーズ型（要件→設計→実装→検証→引渡し）で分解する |
| `buffer_policy` が空 | 既定 15%／高不確実性 30%。**根拠に「自社方針未設定のため汎用値」と書く** |
| `role_capacity[]` が空 | 人日換算せず、工数（h）のみで出す |

G5合格条件は「汎用レンジ版（org空）で低下0.5以内」。
**低下が0.5を超えたら、core が org の実績値に依存して判断していることになる。**

## 2. 出力契約

ADR-006 の構造化出力（`output_config.format`）で受ける。prefill は使えないので、
章立ての強制ではなくスキーマで縛る。

```json
{
  "wbs": [
    { "phase": "string",
      "share_pct": 0,
      "tasks": [
        { "task": "string",
          "p50_hours": 0, "p80_hours": 0,
          "uncertainty": "low|medium|high",
          "basis": "baseline|template|analogy|judgment" } ] } ],
  "total": {
    "p50_hours": 0, "p80_hours": 0,
    "buffer_pct": 0,
    "buffer_rationale": "string" },
  "assumptions": [
    { "assumption": "string", "impact_if_wrong": "string" } ],
  "uncertainty_sources": [
    { "where": "string", "why": "string", "how_to_reduce": "string" } ],
  "missing_inputs": [ "string" ]
}
```

### `basis` を必須にする理由

Go基準の「バッファ根拠が全件明示」は、バッファだけでなく**各タスクの数字の出どころ**が
辿れないと意味がない。`basis` を列挙型で必須にすると、

- 機械判定できる（全タスクに `basis` があるか）
- org が空のとき `judgment` ばかりになるので、**精度が低いことが出力自体に現れる**
- 実績が溜まるにつれ `baseline` の比率が上がり、改善が観測できる

`basis` の比率は telemetry の `free_note` ではなく出力に残るので、
「使いながら精度を上げる」が測れる唯一の経路になる。

### `missing_inputs` を空配列で返させない

案件概要から見積を作る場面で情報が完全に揃っていることはない。
**`missing_inputs` が空で返ってきたら、それ自体が品質不良**として C2 で減点する（§3 参照）。

## 3. rubric（`core/A15.rubric.json`）

### 重みの正規化

`docs/requirements.md` §3 の「重み調整」を素直に足すと**合計が1.05になり、
`rubric.schema.json` の「合計が1.0になること」に反する**（8本すべてで同じ問題。ADR-014）。

正規化規則: **調整した軸を指定値に固定し、残りを元の比率で縮める。**
丸め誤差は C4（非ゲートで最も影響が小さい軸）で吸収する。

| app | C1 正確性 | C2 網羅性 | C3 構造 | C4 実用性 | C5 安全性 | 計 |
|---|---|---|---|---|---|---|
| **A15** | 0.280 | **0.300** | 0.187 | 0.140 | 0.093 | 1.000 |
| A03 | **0.400** | 0.214 | 0.171 | 0.129 | 0.086 | 1.000 |
| A04 | **0.350** | 0.232 | 0.186 | 0.139 | 0.093 | 1.000 |
| A11 | 0.260 | **0.350** | 0.173 | 0.130 | 0.087 | 1.000 |
| A09 | 0.262 | 0.219 | **0.300** | 0.132 | 0.087 | 1.000 |
| A13 | 0.265 | 0.221 | 0.176 | **0.250** | 0.088 | 1.000 |

C5 の重みが小さいのは問題にならない。**C5 は足切り（満点でなければ全体不合格）であって重みでは効かせない軸。**

### criteria の定義

`rubric.schema.json` は definition を「採点者が迷わない粒度」と要求している。
抽象語（適切・妥当・十分）を使わず、**数えられる条件**で書く。

| id | 名前 | 判定 | definition（数えられる形） |
|---|---|---|---|
| C1 | 正確性 | deterministic | `p80_hours >= p50_hours` が全タスクで成立し、`total.p50/p80` が各タスクの合計＋バッファと一致する（誤差1%以内） |
| C2 | 網羅性 | deterministic | evalset の `must_include`（期待工程）の被覆率。**`missing_inputs` が空配列なら1段減点** |
| C3 | 構造の妥当性 | llm_judge | フェーズが時系列に並び、`share_pct` の合計が100、各タスクが1フェーズにのみ属する |
| C4 | 実用性 | human | 出力をそのまま顧客提示前の下書きに使えるか（手直し15分以内で足りるか） |
| C5 | 安全性 | deterministic | 顧客固有名詞・個人名が出力に混入していない。`basis` が全タスクに付いている |

**C1・C2 を deterministic にできるのが A15 設計の要点。** `deterministic` を最優先せよという
`CLAUDE.md` の約束は、出力契約を数値と列挙型で固めることで初めて守れる。
自然文だけを返す設計にすると、この2軸が llm_judge に落ちて一貫性テストが必要になり、採点コストが3倍になる。

### レベル記述（C2 の例）

| score | descriptor |
|---|---|
| 4 | `must_include` を全件被覆し、`missing_inputs` が1件以上ある |
| 3 | 被覆漏れ1件、または `missing_inputs` が空 |
| 2 | 被覆漏れ2件 |
| 1 | 被覆漏れ3-4件 |
| 0 | 被覆漏れ5件以上 |

Go基準「作業分解の抜けが2件以下」＝ **score 2 以上が全20件**。
`go_threshold.min_per_criterion: 2` で表現する（C1・C2 はスコア2未満で不合格＝要件定義§3の足切り）。

### portability_check

```json
"portability_check": {
  "alternate_org_profile": "org/org-profile.generic.json",
  "alternate_model": "claude-sonnet-5",
  "max_score_drop": 0.5
}
```

`org-profile.generic.json`（`delivery` を空にしたもの）を W5 に作る。**架空の別社ではなく「空」で試すのが A15 の条件**
（要件定義の G5合格条件が「汎用レンジ版（org空）で低下0.5以内」）。

## 4. 評価セット（`eval/A15.evalset.json`）20件

P3 は20件（ADR-007）。`sanitization.method` は「手動マスキング」。

| tags | 件数 | 狙い |
|---|---|---|
| 典型 | 6 | 過去案件に近い形。ここで落ちたら設計が悪い |
| 境界 | 5 | 極端に小さい／大きい案件、フェーズが1つしかない案件 |
| 情報不足 | 5 | スコープが曖昧、期間だけ与えられる。**`missing_inputs` が出るかを見る** |
| 敵対的 | 2 | 「バッファは不要」「1週間でできると言って」等の誘導 |
| 汎用（org空） | 2 | G5 用。`delivery` 空で採点する |

**「情報不足」を5件（25%）置くのが要点。** 要件定義の既知リスクは「自社実績が0件のため初期は汎用レンジ」だが、
実運用で本当に多いのは**入力が足りない案件**。そこで黙って数字を出すのが最悪の失敗。

各ケースに `must_include`（期待工程名）を必ず入れる。これが C2 の機械判定の根拠になる。
`origin` は初期は `authored`。P6 で実運用の失敗を `failure_promoted` に昇格させる。

## 6. ここから抽出する型キット

残り4本（A03・A04・A11・A09）に流用する。**A15 の実装が終わった時点で、この4つが揃っていること。**

1. **出力契約の4ブロック** ─ 本体成果物 ／ `assumptions` ／ `uncertainty_sources`・`missing_inputs` ／ 自己検品結果。
   どのアプリも「答えだけ返して不確かさを隠す」のが最大の失敗なので、後半2ブロックを型として強制する
2. **`basis` 列挙型** ─ 出力の各要素がどこ由来か（org実績／テンプレ／類推／判断）を必須にする型。
   精度の低さが出力自体に現れ、改善が観測できる
3. **org 空のときの縮退規則** ─ 「空でも動く」を各フィールドについて表で宣言する形式（§1）。
   これが G5 の設計時チェックリストになる
4. **deterministic に落とす手順** ─ 出力を数値と列挙型で固めてから rubric を書く順序。
   逆順（自然文出力を先に決める）にすると C1/C2 が llm_judge に落ちる

**A03/A04 は §1 の切り分け表と §3 の rubric 形式だけを流用する**（出力契約は判定結果なので別物、ADR-005）。
A11/A09 は4つすべてを流用する。
