## 2. P1要件定義

### A15 ワークプラン／工数見積キット

- **目的**: 見積の根拠を構造化し、レンジと前提を明示できる状態にする
- **利用者・場面**: 自分／案件着手前・提案時
- **現状値 Before**: 見積作成時間＝`（着手前に実測して記入）`分／乖離率＝`（記入）`%
- **KPI**: 見積作成時間／実績との乖離率（±20%以内）
- **Go基準**: 評価20件で、作業分解の抜けが2件以下かつバッファ根拠が全件明示
- **入力**: 案件概要・スコープ・制約
- **出力**: WBS・工数レンジ（p50/p80）・前提リスト・不確実性の所在
- **データ区分の上限**: 3 社内限
- **HITL**: 顧客提示前に本人が数値を確認
- **既知のリスク**: 自社実績が0件のため初期は汎用レンジ。使いながら実績を蓄積しないと精度が上がらない
- **core / org の切り分け**
  - core: 作業分解の型、不確実性の評価、バッファ算定、レンジ提示のロジック
  - org: `delivery.estimation_baseline[]`, `delivery.role_capacity[]`, `delivery.wbs_templates[]`, `delivery.buffer_policy`

### A14 KPIツリー／ロジックモデル ビルダー

- **目的**: 目的からKPIまでを一直線に接続し、測れない指標を排除する
- **利用者・場面**: 自分・事業企画／構想フェーズ
- **現状値 Before**: KPIツリー設計時間＝`（記入）`分／手戻り回数＝`（記入）`回
- **KPI**: 設計時間／指標の測定可能性（全KPIに測定方法が付くか）
- **Go基準**: 評価20件で、測定方法が未定義のKPIが0件
- **入力**: 目的・事業内容・制約
- **出力**: KPIツリー・測定設計・データ入手可否
- **データ区分の上限**: 3 社内限
- **HITL**: 不要（社内検討用）
- **既知のリスク**: 競合ツールが多い。差別化は測定可能性の判定のみで、そこが弱いと存在価値がない
- **core / org**: core＝目的→中間成果→KPIの分解ロジック、MECE検査、測定可能性の判定 ／ org＝業種別のKPI例示、自社の指標語彙

### A13 As-Is／To-Be プロセス可視化

- **目的**: ヒアリングメモから、合意形成に使えるプロセス図を短時間で作る
- **利用者・場面**: 自分・業務改革案件／ヒアリング直後
- **現状値 Before**: 図化時間＝`（記入）`分／手戻り＝`（記入）`回
- **KPI**: 図化時間／初回提示での合意率
- **Go基準**: 評価20件で、工程の抜けが1件以下かつ分岐が正しく表現される
- **入力**: ヒアリングメモ（箇条書き・議事録）
- **出力**: As-Is図・課題タグ・To-Be案・施策候補
- **データ区分の上限**: 2 顧客機密（匿名化後）
- **HITL**: 顧客提示前に本人が事実確認
- **既知のリスク**: メモの粒度に品質が強く依存する。粗いメモでの挙動を評価セットに必ず含める
- **core / org**: core＝メモ→工程抽出→分岐/例外の補完→課題タグ付け→施策候補の生成 ／ org＝図の体裁のみ

### A11 RFP／提案要件アナライザー

- **目的**: RFPの読み落としをなくし、勝ち筋と落とし穴を着手前に見立てる
- **利用者・場面**: 自分・提案リーダー／RFP受領直後
- **現状値 Before**: 読解・要件整理時間＝`（記入）`分／読み落とし＝`（記入）`件
- **KPI**: 要件抽出の網羅率／読み落とし件数／初動までの時間
- **Go基準**: 評価20件で、必須要件の抽出漏れ0件・落とし穴の検出3件以上
- **入力**: RFP本文（PDF/テキスト）
- **出力**: 要件一覧・評価基準の推定・落とし穴・情報不足箇所・工数レンジ
- **データ区分の上限**: 2 顧客機密（匿名化後）
- **HITL**: 提案方針の決定は必ず人
- **既知のリスク**: 外部文書を読むためプロンプトインジェクションの経路になる。**injection_suite 必須**
- **core / org**: core＝要件抽出、評価基準の逆算、落とし穴の検出、情報不足箇所の指摘 ／ org＝自社の勝ちパターン、過去の失注要因、対応可否の判断基準

### A09 提案書ストラクチャ・ジェネレーター

- **目的**: 論点からストーリーへの変換を型化し、毎回ゼロから考えない
- **利用者・場面**: 自分／提案書作成の着手時
- **現状値 Before**: 骨子作成時間＝`（記入）`分／差し戻し＝`（記入）`回
- **KPI**: 骨子作成時間／自己検品の指摘件数／採択率
- **Go基準**: 評価20件で、課題と打ち手の1対1対応が全件成立
- **入力**: 論点メモ・顧客課題・提案の核
- **出力**: 章立て・各章のメッセージ・スライド構成・検品結果
- **データ区分の上限**: 2 顧客機密（匿名化後）
- **HITL**: 顧客提示前に全面レビュー
- **既知のリスク**: 自社フォーマット癒着が最も強い。**外販は最初から狙わず社内専用と定義する（G5免除）**
- **core / org**: core＝論点の構造化、Minto型の論理検査、汎用20項目の自己検品 ／ org＝章立て、トーン、禁止表現、自社固有の検品項目、出力体裁

### A03 データ投入可否ゲート

- **目的**: 投入前に可否を判定し、誤投入をゼロにする
- **利用者・場面**: 全社員／生成AIに何かを貼る直前
- **現状値 Before**: 判断に迷った回数＝`（記入）`回/週／誤投入インシデント＝`（記入）`件
- **KPI**: 誤投入の未然防止数／判定所要時間（30秒以内）
- **Go基準**: 評価30件で、区分判定の正答率95%以上・**禁止入力の見逃し0件**
- **入力**: 投入予定のテキスト
- **出力**: 可否・該当区分・理由・匿名化案・使用可能ツール
- **データ区分**: 判定対象は全区分（処理はブラウザ内で完結し、外部送信しない）
- **HITL**: conditional判定時は本人が匿名化を確認
- **既知のリスク**: 誤って「可」と出すと事故に直結。**見逃し0件を足切り条件にする**
- **core / org**: core＝区分判定のロジック、匿名化提案、パターン検出 ／ org＝`policy.data_classification[]`, `policy.prohibited_inputs[]`, `policy.approved_tools[]`

### A04 AI利用ポリシー・チェッカー

- **目的**: やろうとしている使い方が規程に触れるかを、事前に自分で確認できる
- **利用者・場面**: AI推進・法務・利用者／新しい使い方を始める前
- **現状値 Before**: 規程確認の所要時間＝`（記入）`分／確認せず実施した割合＝`（記入）`%
- **KPI**: 違反の検出率／是正率／確認所要時間
- **Go基準**: 評価30件で、既知の違反ケースの検出率100%・過検出20%以下
- **入力**: 実施計画文またはプロンプト
- **出力**: 抵触の有無・該当条項・代替案・必要な承認
- **データ区分の上限**: 3 社内限
- **HITL**: 抵触ありの場合は法務確認へ誘導
- **既知のリスク**: 過検出が多いと使われなくなる。検出率と過検出のバランスが設計の要
- **core / org**: core＝計画文/プロンプトを規程に照合するロジック、HITL要否の判定 ／ org＝`policy.*` 全般、`policy.human_approval_required[]`, `policy.disclosure_rules`

### A18 契約書・NDA 一次スクリーニング

- **目的**: 契約の一次確認を構造化し、論点の抜けと差し戻しを減らす
- **利用者・場面**: 自分・法務／契約書受領時
- **現状値 Before**: 一次レビュー時間＝`（記入）`分／指摘の抜け＝`（記入）`件
- **KPI**: レビュー短縮／レッドフラグの検出率／エスカレーション判断の妥当性
- **Go基準**: 評価30件（**合成データ**）で、レッドフラグ検出率100%・誤検出30%以下
- **入力**: 契約書テキスト（**当面は合成データのみ**）
- **出力**: 条項マップ・自社基準との差分・レッドフラグ・エスカレーション要否
- **データ区分の上限**: 1 極秘は不可／2 顧客機密は閉域のみ
- **HITL**: 全件、法務が最終判断（自動判定を最終結論にしない）
- **既知のリスク**: 実データ投入は最終段まで行わない。判定を鵜呑みにする運用が最大のリスク
- **core / org**: core＝条項の分類、自社基準との差分検出、エスカレーション判定 ／ org＝`legal.standard_clauses[]`, `legal.counterparty_types[]`

## 4. ゲート

### 開発フェーズ

| フェーズ | 通過条件 |
|---|---|
| P1 要件定義 | 現状値が**実測**で埋まっていること（推定不可） |
| P2 設計 | core に会社固有語の混入が0件（`check-separation.sh`） |
| P3 プロトタイプ検証 | 加重スコアが閾値超え＋足切り項目を全通過 |
| P4 パイロット | 実測ログが5件以上蓄積 |
| P5 リリース | セキュリティ／ガバナンス審査パス |
| P6 定着・改善 | 四半期レビューで継続/改修/廃止を判定 |

### 外販ゲート

v1.0 は G1〜G3 しか定義しておらず、`CLAUDE.md` の DoD と `rubric.portability_check` が参照する「G5」が存在しなかった。
G4／G5 を定義して整合させた（ADR-003）。

| ゲート | 内容 | 通過条件 | 落ちたときの扱い |
|---|---|---|---|
| G1 | 自分 | 直近4週で、対象タスクが発生した機会のうち80%以上で使用。**機会が3回以上ある場合に限り判定** | **廃棄**（作ったこと自体は習熟として計上）／機会3回未満は判定保留・次期繰越 |
| G2 | チーム | 自分以外2名が各3回以上使用、実測ログ10件以上 | 社内専用として据え置き |
| G3 | 顧客 | 顧客1社でパイロット完了 | 外販は見送り、社内資産として運用 |
| G4 | ガバナンス | セキュリティ／ガバナンス審査パス（P5と同一） | 外販不可。社内利用は継続 |
| G5 | 可搬性 | org-profile 差し替え後のスコア低下が `portability_check.max_score_drop` 以内、かつ代替モデルで動作 | core に会社固有が漏れている。分離をやり直す |

**判定順序は番号順ではない。`G5 → G1 → G2 → G4 → G3`。**
G5 は P3 の採点と同時に判定でき、落ちたときの修正が最も安いので先に置く。番号は識別子であり順序を表さない。
A09 は G5 免除・G3 対象外（社内専用と定義済み）。ただし core／org の分離構造は他と同じに保つ。

**G1 の基準を v1.0 から改めた（ADR-004）。** 旧基準「直近2週の利用が5日以上」は日次利用アプリしか通れない。
RFP・契約書・工数見積・KPIツリーは週5回発生しないため、旧基準では A11／A15／A13 が品質と無関係に自動廃棄される。
**旧基準が測っていたのは業務の発生頻度であって、アプリの価値ではない。**
新基準では「使わなかった機会」も telemetry に1レコード出す（`free_note` に理由）。記録しないと分母が消える。

**確定5本すべてがG3を通ることは想定していない。2〜3本通れば十分。**
G1で落ちたアプリを廃棄することを恥と考えない。使われないアプリを抱え続けるほうが、ポートフォリオ全体の信頼を損なう。
