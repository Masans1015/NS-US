自己検品の結果

⚠ 課題と打ち手が1対1で対応していません。

✓ 各章のメッセージが体言止めでなく主張になっている

この検品ブロックが A09 の価値

章立てを作るだけのツールは既にある。「課題③に打ち手がない」を着手時に指摘されることが本体。
Go基準を「課題と打ち手の1対1対応が全件成立」に置いているのはこのため。

0. v1.0 で何が破綻していたか

検算して見つかった問題を、影響の大きい順に並べる。すべて算術か定義の不整合であり、実装の巧拙とは無関係。

新基準に差し替える。

G1（改定）: 直近4週において、対象タスクが発生した機会のうち 80%以上 でアプリを使ったこと。

5. LLM 呼び出しの標準形

v1.0 は「外部LLM呼び出しは Anthropic API のみ。モデルは差し替え可能な形で定数化」までしか決めていなかった。
実装が始まってから毎回考え直すことになるので、ここで固定する。詳細と根拠は docs/decisions.md の ADR-005／ADR-006。

二層に分ける

層対象LLM理由
決定論層A03・A04使わない全社員に配るアプリで各人にAPIキーを持たせるのは非現実的。区分判定は policy.data_classification と prohibited_inputs[].detect_patterns で機械判定できる。Go基準「見逃し0件」は決定論のほうが達成しやすい
LLM層A15・A11・A09・（A13）使う利用者は自分のみ。APIキーはセッション中のみJS変数で保持（localStorage 禁止は既定通り）

A03／A04 で LLM を使うのは「匿名化案の文面生成」だけに限り、キー未入力でも本体機能が完全に動く構成にする。
これは制約への妥協ではなく、外販性◎の2本を「導入時にAPIキー調達が不要な製品」にするという設計判断。

呼び出し規約

const MODEL = { PRIMARY: 'claude-opus-5', ALT: 'claude-sonnet-5' };
  • モデルIDに日付サフィックスを付けない。ALT は G5 可搬性テストの代替モデル
  • thinking: { type: 'adaptive' }。budget_tokens は Opus 5／Sonnet 5 では 400 エラーになる
  • 深さは output_config.effort（既定 high、単純な抽出は low）で制御する
  • 出力は output_config: { format: {...} } の構造化出力。assistant prefill は 400 エラーなので使えない → core は構造化データを返し、体裁は render 層が解釈する。3層分離とそのまま一致する
  • stop_reason === 'refusal' を必ず確認する。A04（規程違反の判定）と A18（レッドフラグ検出）は安全性分類器に拒否される経路がある。 サーバサイドフォールバックを既定で入れる
  • 長文（RFP・契約書）は streaming。非streaming の max_tokens は 16000 目安
  • プロンプトキャッシュ: core の system prompt ＋ org-profile を prefix に置き cache_control。1024トークン未満はキャッシュされない
  • トークン数は count_tokens エンドポイントで測る。他社トークナイザで代用しない

A11 の網羅率を機械検証する

A11 の Go基準は「必須要件の抽出漏れ0件」だが、v1.0 には検証手段がなかった。

RFP の PDF を base64 の document ブロックで直接投入し、citations: { enabled: true } を付ける。
出力の各要件に出典（ページ番号）が付くので、抽出漏れを人が原文と突き合わせて確認できる。
上限は32MB／600ページ（1Mコンテキストモデル）。これを超えるRFPは分割する。

C2（網羅性）の check_method を deterministic にできるかはこの出典が付くかどうかで決まる。
W8 の最初の作業は Citations の動作確認にする。動かなければ C2 は human 判定に落とす（docs/requirements.md §3 の一貫性テストの手順と同じ扱い）。

ADR-001 稼働時間の前提を174hに固定する

判断: 計画の基礎を「平日3h／日・祝日は稼働0」＝13週で 174h とする。「週15h」は努力値として扱い、計画の基礎に使わない。

理由: 2026年9〜11月に祝日が6日ある（9/21・9/22・9/23・10/12・11/3・11/23）。
13週×15h＝195h の前提は21h過大。とくに W4（9/21-27）は平日2日で稼働6hしかなく、この週に集中作業を置くと確実に遅れる。

影響: docs/plan.md §1 の週別稼働時間表が唯一の基礎になる。祝日に稼働できた分はバッファの回復として扱い、計画の前提には織り込まない。

ADR-002 ポートフォリオを確定5本＋条件付き1本に縮小する

判断: A15・A03・A04・A11・A09 を確定。A13 を条件付き（W11時点で残バッファ15h以上なら着手）。A18・A14 を次期送り。

理由: 必要工数219h（基盤27h＋実装156h＋未計上36h）に対し稼働174h。超過45h。
楽観ケース（195h）でも24h超過するので、稼働時間の前提を変えても結論が変わらない。
確定5本なら131h（実装102h＋未計上29h）で、稼働174hに対しバッファ43h（25%）。

「未計上分を諦めて8本やる」は成立しない。諦める対象が評価セット作成なので、P3ゲートを通せず telemetry も集計されず、外販根拠がゼロのまま8本のプロトタイプが残る。13週の目的を失う。

A18 を落とした理由は重要度ではなく 13週内に G1 へ到達する構造がないこと。契約書の受領頻度が低く、実データ投入も最終段まで行わない方針なので、今期の成果は「合成データで評価スコアが出た」に留まる。実データを扱える条件が整った期に回すほうが実入りが大きい。

影響: docs/requirements.md §1 の8本の要件定義は残す（次期に使う）。着手対象のみ docs/plan.md §2 が上書きする。

代替案と棄却理由: A14/A13 の2本だけ落とす（-30h＋未計上分の減少で実質-34h）→ 必要185h、まだ11h超過。
バッファなしで13週走ることになり、1回の遅れで復帰不能。

ADR-003 ゲート番号を G1〜G5 に確定し、判定順序を明示する

判断: G1 自分／G2 チーム／G3 顧客／G4 ガバナンス審査（新設）／G5 可搬性（定義）。
判定順序は番号順ではなく G5 → G1 → G2 → G4 → G3。

理由: CLAUDE.md の DoD と rubric.portability_check が「G5」を参照しているのに、
docs/requirements.md のゲート表には G1〜G3 しかなく、G4/G5 が未定義だった。参照先のない条件は運用されない。

G5 を先頭に置くのは、P3の採点と同時に判定でき、落ちたときの修正（core からの分離やり直し）が最も安いから。

2. 出力契約

ADR-006 の構造化出力（output_config.format）で受ける。prefill は使えないので、
章立ての強制ではなくスキーマで縛る。

{
  "wbs": [
    { "phase": "string",
      "share_pct": 0,
      "tasks": [
        { "task": "string",
          "p50_hours": 0, "p80_hours": 0,
          "uncertainty": "low|medium|high",
          "basis": "baseline|template|analogy|judgment" } ] } ],
  "total": {
    "p50_hours": 0, "p80_hours": 0,
    "buffer_pct": 0,
    "buffer_rationale": "string" },
  "assumptions": [
    { "assumption": "string", "impact_if_wrong": "string" } ],
  "uncertainty_sources": [
    { "where": "string", "why": "string", "how_to_reduce": "string" } ],
  "missing_inputs": [ "string" ]
}

basis を必須にする理由

Go基準の「バッファ根拠が全件明示」は、バッファだけでなく各タスクの数字の出どころが
辿れないと意味がない。basis を列挙型で必須にすると、

  • 機械判定できる（全タスクに basis があるか）
  • org が空のとき judgment ばかりになるので、精度が低いことが出力自体に現れる
  • 実績が溜まるにつれ baseline の比率が上がり、改善が観測できる

basis の比率は telemetry の free_note ではなく出力に残るので、
「使いながら精度を上げる」が測れる唯一の経路になる。

missing_inputs を空配列で返させない

案件概要から見積を作る場面で情報が完全に揃っていることはない。
missing_inputs が空で返ってきたら、それ自体が品質不良として C2 で減点する（§3 参照）。

4. 評価セット（eval/A15.evalset.json）20件

P3 は20件（ADR-007）。sanitization.method は「手動マスキング」。

tags件数狙い
典型6過去案件に近い形。ここで落ちたら設計が悪い
境界5極端に小さい／大きい案件、フェーズが1つしかない案件

「情報不足」を5件（25%）置くのが要点。 要件定義の既知リスクは「自社実績が0件のため初期は汎用レンジ」だが、
実運用で本当に多いのは入力が足りない案件。そこで黙って数字を出すのが最悪の失敗。

各ケースに must_include（期待工程名）を必ず入れる。これが C2 の機械判定の根拠になる。
origin は初期は authored。P6 で実運用の失敗を failure_promoted に昇格させる。

A03・A04 判定ロジック詳細設計（LLM非依存）

対象週: A03 = W6（10h）／A04 = W7（12h）
前提: ADR-005（LLM非依存）、docs/requirements.md の A03・A04 節

この2本は利用者が全社員で、外販性◎の主力。policy ブロックを共有するが、
判定の倒し方は逆（§4）。共有するのはデータだけで、閾値設計は別物。

1. 設計の中心となる制約

自由文からデータ区分を当てることは原理的にできない

A03 の入力は「投入予定のテキスト」。ここから区分を推定しようとすると壁に当たる。

  • 匿名化済みの顧客資料は、見た目が社内文書と区別できない。 顧客名を伏せた議事録は、 文面上は社内会議のメモと同じ。level 2 と level 3 を機械で分けられない
  • 逆に「社内規程」と「顧客の社内規程」も文面が似る
  • 判定を外すと、A03 の足切り「禁止入力の見逃し0件」を守れない

したがって、区分は利用者に選ばせる（ADR-013）。機械が担うのは次の2つに絞る。

機械が担う人が担う
禁止入力の検出（detect_patterns の正規表現）データ区分の選択
選ばれた区分に対する可否・条件・使用可能ツールの導出迷ったときにどちらを選ぶか
匿名化すべき箇所の指摘匿名化の実施と確認

これは機能の後退ではない。判定所要時間30秒以内というKPIに対し、
区分の選択は数秒で終わり、規程の条文を引く部分（時間がかかる部分）を機械が肩代わりする。

Go基準の読み替えが必要

要件定義は「評価30件で、区分判定の正答率95%以上・禁止入力の見逃し0件」と書いている。
区分を利用者が選ぶ設計では、前半は次の意味になる。

選択された区分に対する 可否・条件・使用可能ツールの導出の正答率が95%以上

導出は policy の参照だけなので、実装が正しければ100%になる。
したがって A03 の実質的な合否は「禁止入力の見逃し0件」に集約される。
評価30件の設計もそこへ寄せる（§5）。

要確認: この読み替えは要件定義の解釈変更にあたる。W6 着手前（10/04まで）に確定させる。
確定しない場合は「区分の自動推定を補助表示として出し、正答率はその補助表示に対して測る」で進める。

2. A03 判定木

上から順に評価し、最初に確定した時点で打ち切る。

入力テキスト ＋ 利用者が選んだ区分
│
├─ 1. prohibited_inputs[] の detect_patterns を全件走査
│     ヒット → 【不可】
│              該当 label / rationale / source_document を表示
│              マッチ箇所をハイライト
│     ※区分によらず禁止。区分判定より必ず先に評価する
│
├─ 2. 選択区分の ai_input を見る
│     "prohibited"  → 【不可】 definition と examples を表示
│     "allowed"     → 【可】   allowed_tools を表示
│     "conditional" → 3へ
│
├─ 3. conditions[] を表示し、【条件付き可】
│     allowed_tools（∩ approved_tools[].status === "approved"）を表示
│     detect_patterns のうち「禁止ではないが要匿名化」のものを走査し、
│     マスク候補として提示
│
└─ 4. 匿名化案の文面生成（任意・LLM）
      LLM.available() === false でも 1〜3 は完全に動く

実装上の要件

  • 正規表現は detect_patterns から読む。コードに書かない。 書いた瞬間に外販時の差し替えが効かなくなる
  • 正規表現の実行はブラウザ内。入力テキストを外部送信しない（要件定義の「処理はブラウザ内で完結」）
  • detect_patterns が不正な正規表現なら起動時に停止する。実行時に黙って false を返すと見逃しになる
  • マッチ箇所のハイライトは、RegExp の d フラグ（hasIndices）で位置を取る
  • 走査は全パターンを実行する。1件ヒットで打ち切らない。「他にも触れている」を全部見せる

出力

{
  "verdict": "prohibited | conditional | allowed",
  "matched_prohibitions": [
    { "label": "...", "rationale": "...", "source_document": "...",
      "matches": [{ "text": "...", "start": 0, "end": 0 }] } ],
  "classification": { "level": 3, "label": "社内限", "ai_input": "conditional" },
  "conditions": ["..."],
  "usable_tools": [{ "name": "...", "max_data_level": 3, "restrictions": ["..."] }],
  "anonymization_targets": [{ "text": "...", "reason": "...", "suggestion": "..." }]
}

source_document を必ず出す。「なぜ不可なのか」を規程の条番号で示せないと、利用者は判定を信用せず回避する。

3. A04 判定ロジック

A04 の入力は「実施計画文またはプロンプト」。ここも自由文の全文マッチに頼らない。
構造化された質問に答えさせ、policy と照合する。

入力（構造化）

項目参照する org フィールド

照合規則

1〜6 は構造化入力に対する照合なので過検出が原理的に発生しない。
過検出が出るのは 7 だけ。ここを絞ることで「過検出20%以下」を守る（§4）。

  "violations": [{ "check": 1, "reason": "...", "clause": "...", "alternative": "..." }],
  "required_approvals": ["..."],
  "disclosure_statement": "...",
  "next_action": "法務確認へ | 承認申請へ | そのまま実施可"
}

「抵触あり」で終わらせず alternative と next_action を必ず出す。
要件定義の既知リスクが「過検出が多いと使われなくなる」なので、
止めるだけの出力は使われなくなる方向に働く。

4. 2本で閾値の倒し方が逆になる

同じ policy を読むのに、最適化の方向が反対。ここを混同すると両方壊れる。

A03A04
Go基準禁止入力の見逃し0件（足切り）検出率100%・過検出20%以下
優先する誤り過検出は許容見逃しも過検出も許さない
迷ったときの倒し方厳しい側（より機微な区分・不可寄り）構造化入力で曖昧さを消す（倒さない）
事故の形誤って「可」と出す → 情報漏洩過検出が多い → 使われなくなり規程が空文化

したがって:

  • A03 の detect_patterns は再現率優先で書く。過検出は conditional（条件付き可）が吸収する
  • A04 は自由文マッチ（検査7）を最小限にする。 検査1〜6の構造化照合を主経路にする
  • 同じ正規表現セットを両アプリで同じ厳しさに使わない。 A04 は検出したものを 「注意」として出し、verdict を直ちに prohibited にしない（検査7のみ）
