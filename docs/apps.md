# 作るもの ─ 5本の具体像

「何が動くのか」を入力と出力の実物で示す。抽象的な目的・KPIは `docs/requirements.md`。

> **入出力の例はすべて「たたき台」。** 実際の案件文書ではなく、形を見せるために書いた架空の例。
> 数値（p50/p80・工数）は Before 実測前なので**仮の値**。実測後に置き換える（`docs/baseline-measurement.md`）。
> **例が的外れなら、そこが要件の認識ズレ。** 実装前にここを直す。

---

## A15 ワークプラン／工数見積キット

**「この案件、何人月？」と聞かれてから、根拠つきで答えるまでを短縮する。**

| | |
|---|---|
| 誰が | 自分（提案リーダー） |
| いつ | 案件の着手前・提案時 |
| 入力 | 案件概要のテキスト（フリー） |
| 出力 | WBS・工数レンジ・バッファ根拠・前提・不確実性・不足情報 |
| LLM | 使う（Opus 5） |

### 入力の例

```
製造業（従業員800名）向け、生産管理領域のAI活用構想策定。期間3ヶ月。
現状ヒアリング → 課題整理 → AI適用候補の洗い出し → ロードマップ策定まで。
体制はマネージャー1名＋コンサル2名を想定。
```

### 出力の例

**WBS**（各タスクに p50 / p80 と、その数字の出どころ）

| フェーズ | タスク | p50 | p80 | 出どころ |
|---|---|---|---|---|
| 要件・KPI定義 15% | 対象業務の選定 | 8h | 12h | テンプレ |
| | 現状値の実測 | 12h | 20h | 判断 |
| | Go基準の設定 | 4h | 6h | テンプレ |
| 設計 20% | 処理フロー設計 | 16h | 24h | テンプレ |
| | 評価設計 | 8h | 14h | 判断 |
| 試作・検証 40% | 最小構成の実装 | 40h | 60h | 類推 |
| | 評価セットで採点 | 16h | 28h | 判断 |
| 効果測定 15% | Before/After比較 | 12h | 18h | テンプレ |
| 報告・引渡し 10% | 報告書作成 | 16h | 22h | 実績 |

**合計 p50 240h ／ p80 340h ／ バッファ 30%**
> バッファ根拠: 高不確実性。「現状値の実測」が自社で未経験の領域であり、前処理と例外処理で過少見積になりやすい

**前提**（外れたときの影響つき）
- ヒアリング対象は3部門以内 → 外れると +40h
- 既存システムの仕様書が提供される → 提供されない場合 +24h

**不確実性の所在**（減らす方法つき）
- 生産管理システムの現行仕様が不明 → キックオフ前に system landscape を1枚もらう

**不足情報** ─ 予算レンジ／意思決定者／既存のAI活用実績

### この出力が効く理由

「出どころ」が全タスクに付く。**実績が0件のうちは「判断」「類推」ばかりになり、精度の低さが出力自体に現れる。**
使い込んで実績が溜まると「実績」の比率が上がるので、**アプリが育ったことを数字で示せる。**

## A03 データ投入可否ゲート

**生成AIに何か貼る直前、30秒で「貼っていいか」を決める。**

| | |
|---|---|
| 誰が | **全社員**（外販性◎の本命） |
| いつ | AIに貼る直前 |
| 入力 | 貼ろうとしているテキスト ＋ データ区分を4択で選ぶ |
| 出力 | 可否・理由（規程の条番号）・使えるツール・匿名化すべき箇所 |
| LLM | **使わない**（ADR-005。全社員にAPIキーは配れない） |

### 入力の例

区分の選択: `2 顧客機密`

```
○○製造の田中部長から共有された来期生産計画。生産能力は現行比120%を想定。
不明点は tanaka@example.co.jp まで。
```

### 出力の例

> ## 不可
> **禁止入力を検出しました。この内容は投入できません。**
>
> | 検出 | 該当箇所 | 根拠 |
> |---|---|---|
> | 個人情報（氏名と他の識別子の組合せ） | `田中部長` | 個人情報取扱規程 |
> | 認証情報・連絡先 | `tanaka@example.co.jp` | 同上 |
>
> **匿名化案**
> `田中部長` → `A社の製造部門責任者` ／ `tanaka@example.co.jp` → （削除）
> `○○製造` → `A社`
>
> 匿名化すると **条件付き可** になります。
> 条件: 顧客との契約でAI利用が禁止されていないことを確認／学習利用オフが担保されたツールのみ
> 使えるツール: Claude (Team)（最大区分3・学習利用オフ）

### 設計の要点

- 検出は `org-profile` の正規表現で行う。**コードに規程を書かない**ので、他社にはプロファイル差し替えだけで移せる
- 区分は**利用者が選ぶ**（ADR-013）。匿名化済みの顧客資料は文面上、社内文書と区別できないため
- 「不可」で終わらせず**必ず匿名化案を出す**。止めるだけのツールは使われなくなる

## A04 AI利用ポリシー・チェッカー

**新しい使い方を始める前に、規程に触れるかを自分で確認できる。**

| | |
|---|---|
| 誰が | AI推進・法務・利用者 |
| いつ | 新しい使い方を始める前 |
| 入力 | **5項目のフォーム**（自由文ではない） |
| 出力 | 抵触の有無・該当条項・代替案・必要な承認・開示文 |
| LLM | **使わない**（ADR-005） |

### 入力の例

| 項目 | 選んだ内容 |
|---|---|
| やること | 顧客提案書のドラフトをAIに書かせる |
| 使うツール | Claude (Team) |
| 投入する最も機微な区分 | 2 顧客機密 |
| 成果物を社外に出すか | 出す |
| 該当する操作 | 顧客への外部送信を伴う成果物の確定 |

### 出力の例

> ## 条件付きで実施可
>
> | 検査 | 結果 |
> |---|---|
> | ツールが承認済みか | ✓ Claude (Team) は approved |
> | 区分がツールの上限内か | ✓ 区分2 ≦ 上限3 |
> | 学習利用オフが担保されているか | ✓ |
> | 人間承認が必要か | **必要** ─「顧客への外部送信を伴う成果物の確定」に該当 |
> | 社外提出時の開示が必要か | **必要** |
>
> **満たすべき条件**
> 1. 顧客名・固有名詞を匿名化したうえで投入する
> 2. 顧客との契約でAI利用が禁止されていないことを確認する
> 3. 顧客提示前に本人が全面レビューする
>
> **付記する開示文**
> 「本資料の作成にあたり生成AIを補助的に使用し、内容は当社が確認しています。」
>
> **次の行動** ─ 匿名化したうえで実施可。法務確認は不要。

### なぜフォーム入力なのか

自由文を読んで規程違反を当てにいくと**過検出が増える**。A04 の Go基準は「過検出20%以下」。
5項目の構造化入力に対する照合なら、過検出が原理的に発生しない（`docs/specs/A03-A04-logic.md` §4）。

## A11 RFP／提案要件アナライザー

**RFPを受け取った直後、読み落としをゼロにして勝ち筋と落とし穴を見立てる。**

| | |
|---|---|
| 誰が | 自分（提案リーダー） |
| いつ | RFP受領直後 |
| 入力 | RFPのPDF（そのまま投入。最大600ページ） |
| 出力 | 要件一覧（**出典ページつき**）・評価基準の推定・落とし穴・不足情報・工数レンジ |
| LLM | 使う（Opus 5・Citations 有効） |

### 入力の例

`AI活用構想策定支援業務_委託仕様書.pdf`（48ページ）

### 出力の例

**必須要件 23件**（抜粋。すべてに出典ページが付く）

| # | 要件 | 種別 | 出典 |
|---|---|---|---|
| 1 | 週次で進捗報告会を実施すること | 必須 | p.12 |
| 2 | 成果物はすべて日本語で作成すること | 必須 | p.31 |
| 3 | 中間報告を2回実施すること | 必須 | p.13 |
| 4 | 再委託は事前承認を要する | 必須 | p.36 |

**評価基準の推定** ─ 価格30% ／ 実績30% ／ 提案内容40%（p.44 の配点表から逆算）

**落とし穴 4件**

| 落とし穴 | 出典 | 提案時の打ち手 |
|---|---|---|
| 検収条件が「発注者が満足すること」と主観的 | p.38 | 検収基準を提案書側で具体化して合意を取る |
| 成果物の著作権が全面的に発注者帰属 | p.36 | 汎用ノウハウの留保を明記する |

**情報不足** ─ 対象部門数が未記載／既存システムの一覧なし／予算レンジ非公開

**工数レンジ** ─ p50 320h ／ p80 460h（A15 の見積ロジックを流用）

### 出典ページが決定的な理由

「読み落とし0件」を主張するには、**人が原文と突き合わせて確認できる**必要がある。
出典が付けば、抜けの検査を機械判定に落とせる（`deterministic`）。
出典が取れなければ網羅性の判定は人手に戻る ─ **W8初日に最初に確かめること**（`docs/plan.md` §7-5）。

## A09 提案書ストラクチャ・ジェネレーター

**論点メモから提案書の骨子へ。毎回ゼロから考えない。**

| | |
|---|---|
| 誰が | 自分 |
| いつ | 提案書作成の着手時 |
| 入力 | 論点メモ・顧客課題・提案の核 |
| 出力 | 章立て・各章のメッセージ・スライド構成・**自己検品結果** |
| LLM | 使う（Opus 5） |
| 外販 | **しない**（社内専用。自社フォーマット癒着が最も強い） |

### 入力の例

```
顧客課題: 見積のばらつきが大きく、失注が続いている
提案の核: 見積プロセスの標準化とAI支援
論点: 属人化 / 実績データが蓄積されていない / 現場に標準化への抵抗がある
```

### 出力の例

| 章 | 枚数 | その章で言い切るメッセージ |
|---|---|---|
| エグゼクティブサマリー | 1 | 見積のばらつきの原因は個人の能力差ではなく、実績が蓄積されない仕組みにある |
| 課題認識 | 3 | ①属人化 ②実績データの不在 ③標準化への現場の抵抗 |
| 打ち手 | 5 | ①見積テンプレートの型化 ②実績記録の仕組み化 |
| 進め方・体制 | 3 | 3ヶ月・2フェーズ。第1フェーズで型を作り、第2で回して実績を溜める |
| 費用 | 1 | 根拠つきで提示 |

**自己検品の結果**

> ⚠ **課題と打ち手が1対1で対応していません。**
> 課題③「標準化への現場の抵抗」に対応する打ち手がありません。
> 打ち手を追加するか、課題③を落としてください。
>
> ✓ 各章のメッセージが体言止めでなく主張になっている
> ⚠ 数値に出典が付いていないスライドが2枚あります（打ち手②、費用）
> ✓ 禁止表現（「革新的な」「シームレスに」「圧倒的な」）の混入なし

### この検品ブロックが A09 の価値

章立てを作るだけのツールは既にある。**「課題③に打ち手がない」を着手時に指摘されること**が本体。
Go基準を「課題と打ち手の1対1対応が全件成立」に置いているのはこのため。

## 5本の関係

```
        A15 工数見積キット  ← 最初に作る。ここから「型キット」を抽出する
         │
         ├──→ A11 RFPアナライザー   （A15の見積ロジックを流用）
         │
         └──→ A09 提案書ストラクチャ（A15の出力契約の型を流用）

        A03 データ投入可否ゲート
         │  policy ブロックを共有
         └──→ A04 ポリシー・チェッカー
```

- **A15 を最初に作る理由**: 他の2本が依存する。ここで型を間違えると3本作り直しになる
- **A03 → A04 の順にする理由**: A03 で `policy` の読み方を確立し、A04 が承認・開示の検査を足す形にすると手戻りが出ない
- **A03・A04 だけ LLM を使わない**: 全社員が使うのでAPIキーを配れない。結果として**導入時にキー調達が不要な製品**になり、外販性が最も高い

## 13週で何が「動く」ようになるか

| 時点 | 動くようになるもの |
|---|---|
| W2末 09/13 | （基盤）telemetry が記録・出力・集計できる。org-profile を読んで起動検証が通る |
| **W5末 10/04** | **A15 が動く。** 案件概要を貼るとWBSとレンジと前提が出る |
| **W6末 10/11** | **A03 が動く。** 貼る前の可否が30秒で分かる |
| **W7末 10/18** | **A04 が動く。** 新しい使い方の可否を自分で確認できる |
| **W9末 11/01** | **A11 が動く。** RFPのPDFを入れると出典つき要件一覧が出る |
| **W11末 11/15** | **A09 が動く。** 論点メモから骨子と検品結果が出る |
| W12 11/22 | A03・A04 を他2名に配布（G2着手） |
| W13 11/29 | 実測した telemetry から削減時間を算出。次期の判断 |

**5本すべてが11/15に揃う。** 残り2週は「使って測る」ための時間で、機能追加はしない。
測らなければ、13週かけて何が良くなったかを一切主張できないため（`docs/plan.md` §6）。
